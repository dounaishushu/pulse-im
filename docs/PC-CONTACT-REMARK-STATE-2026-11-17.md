# PC 好友备注框置灰修复

对应 PC **2.4.173 / Windows x64**，2026-11-17。

## 原因与边界

备注框依据资料接口的 `is_contact` 启用。服务端仅允许为当前账号的真实好友保存备注，内部员工强加好友也会写入同一张正式好友关系表；仍能打开聊天会话，不等于好友关系仍然存在。

用户确认重新添加该好友后备注恢复，这与好友关系识别/刷新问题一致。代码还存在确定的状态更新缺口：资料页首次读到非好友状态后，不再复核；好友在另一个入口或设备添加成功、通知更新后，这张已打开的资料卡仍保持置灰。使用完整 PC 页面和模拟旧响应复现该缺口，修复前两项检查均失败。

现有信息无法判定该具体账号此前属于关系未建立、关系后来失效，还是读取了较早状态。本次没有查询或修改生产数据库中的该账号关系，也没有根据聊天存在或内部员工身份直接放开备注权限。

## 修复

- 资料首次返回非好友时，独立读取当前好友关系；确认已成为好友后，在原资料卡直接启用备注、显示已保存的备注，不重载聊天页面。
- 资料仍只读时，收到好友通知、实时认证恢复或收件箱恢复通知会再次复核。合并同一资料卡的并发检查；已经可编辑的资料卡不因通知重读并覆盖正在输入的备注。
- 未确认关系时显示原因及“刷新好友状态”。内部员工可点击“添加好友并备注”，等待服务端添加成功及最新关系确认后启用备注框。普通用户没有强加入口；添加被拒绝、确认失败和账号切换都不会误开放输入。
- 添加后的确认等待此前尚未完成的关系读取结束，再进行新查询，避免添加前的旧响应影响确认结果。关闭资料页或切换账号后，迟到响应不能重新打开或污染新资料。
- 新增客户端内部 `/contacts/relationship` 映射，读取现有服务端 `/profiles/{id}`，保留群上下文、登录代次和取消信号，不加载头像。备注保存的版本预读也不再等待头像授权，保留备注/分组语义、字符串版本号及冲突拒绝。

无需新增或部署服务端接口。原有搜索结果中强加好友后打开资料的流程保留。

所有页面验证使用本机夹具和模拟响应，没有向生产账号发好友请求或写入备注。

- 客户端单元检查 **123 项通过**。新增五项覆盖不等待头像的备注保存、大整数版本号、群上下文及关系结果、资料权限拒绝、切换账号阻止写入、版本冲突不覆盖。
- 既有群发检查 **19 项通过**，覆盖备注搜索与分页勾选、账号隔离，以及关窗续发、停止/重试等行为。
