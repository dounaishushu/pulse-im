# 接口契约与业务逻辑审查

日期：2026-11-16。代码基线：`7638d465af153c211aaee3f86f7697fc8a68b341`。

本轮检查的是接口语义、错误处理、重试、权限和状态边界。范围包括 Go 消息/回执/清空记录、群发转发任务及 PC、Android、iOS 的 Go 适配层。当前修改在本地隔离环境验证，**尚未部署服务器，也没有发布新客户端安装包**。未更改生产用户、消息或管理员配置。

## 已确认的问题和修复

### 1. 头像错误被转换成成功响应

PC/Web 的个人资料、联系人、通知头像等分支使用不区分原因的 `catch`。401、429、503，以及页面取消，都可能变成空头像并返回成功；批量媒体授权也只传播 401。Android 的批量授权对单项 503 没有保留错误，可能改走单项请求；iOS 作业头像及群头像也存在 `try?` 吞异常。

本批仅对确定不可访问的 403/404 使用默认头像。登录失效、取消、限流、服务故障及格式异常继续向调用方传播。账号切换与晚到响应的既有保护保留。

位置：`client-shared/go-v2.js`、`android/app/src/main/java/com/pulseim/android/GoV2Api.kt`、`ios/PulseIM/GoV2Adapter.swift`。共享 JS 同步到 PC/Web 发布副本。

### 2. 单条回执改变了更早消息的已读状态

PC 适配层把 `message_id` 或 `message_ids` 的最大值直接送往范围已读接口，单条事实被错误扩大为之前全部消息。iOS `markMessageRead` 的 Go 分支也使用了范围接口；安卓适配层只识别范围回执，未实现单条回执契约。

本批明确区分：`through_message_id` 调用连续范围接口；单条/列表调用逐条回执接口。先验证整个 ID 列表，拒绝重复、超限、混合单条与范围参数。服务端已存在的逐条回执实现继续作为真相来源，不新造另一套已读规则。

真实隔离服务验证：读第二条后，第一条仍未读，用户 `read_seq` 保持 0。

### 3. “已送达”被当作“已读”，非法状态也可能默认已读

Android/iOS 的适配分支固定调用 `/read`；PC 对不是 `delivered` 的值默认当 `read`，拼错状态也会修改已读。

三端现在只接受 `read`、`delivered`；缺省保留既有 `read` 契约。无效输入在发出请求前拒绝；已送达使用 `/delivered`，不推进已读水位。逐条回执返回服务端真实状态，不把已经是 `read` 的消息降为 `delivered`。

### 4. PC 范围已读返回缺少未读数

`pc/web/conversation-read.js` 明确校验 `unread_count`，适配层却未提供。服务器成功后，客户端可能仍判断返回值不合格，造成重试和状态不一致。

本批在范围操作完成后读取服务端未读结果，返回 `unread_count`、`unread_truncated`、操作状态及原请求边界。没有用消息序号相减估算，保留旧逐条回执语义。

### 5. 移动端清空历史的边界会随执行时间变化

Android/iOS 每次操作都重新查询 `message_seq`，忽略调用时选择的范围。同一清空操作在新消息到达后重试，可能扩大清空范围。

本批在确认框打开时固定当前消息范围，将边界显式传入 API；Go 适配层要求该参数，缺少时拒绝执行。原 PHP 分支仍按既有契约发送。服务端原有单调清空和重试处理无需修改。

真实隔离服务验证：清空旧边界、收到新消息、用相同边界重试后，新消息仍可见。这里只处理该用户的历史视图，不删除对方记录。

### 6. 重复转发来源或目标能够重复入队

Go 的 `/forward-batches` 与 `/broadcasts` 只限制数组长度，没有拒绝重复目标；转发也接受重复来源。后续每项具有不同序号，消息幂等键无法把这些重复项合并。

本批在入口验证 UUID、数量及唯一性。重复选择返回 400，整个任务不入队。没有对计划任务的多步骤内容做去重，合法的重复发送步骤语义不变。

位置：`server/internal/core/delivery_jobs.go`。

### 7. 取消任务不具备安全重试语义，错误码也混淆

原取消接口仅执行一次条件 UPDATE：已经取消、已完成、不存在和他人任务都可能返回 409；收到旧身份后没有在事务内再次核验登录。

本批取消操作在事务内重新验证身份并锁定所属任务。已经取消返回 204，已完成返回 409，不存在或不属于当前用户返回 404。保持与执行 worker 的锁顺序一致，不能取消管理员创建的任务。

位置：`server/internal/core/delivery_controls.go`。回归覆盖重复取消、所有权、已完成状态、会话撤销以及取消后不再执行。

### 8. 不存在的管理员分发任务被报告为服务器繁忙

停用/删除分发任务时，查询不到记录的错误直接进入通用 503，客户端可能按临时故障重试。

本批将确定不存在的记录转换为 404，其余数据库错误保留原错误。位置：`server/internal/core/delivery_controls.go`。

## 实现方面的进一步判断

- 部分适配器把一次用户动作拆成“更新字段、修改开关、更新头像、再次查询”多个写请求。任一步失败都可能留下部分已修改状态。后续宜由服务器提供与用户动作对应的事务接口；多步任务则要明确返回每一步结果。不能统一把任意 PATCH 自动重放。
- 多处单项回执、群设置、成员和联系人响应仍在客户端手工重新拼装，字段容易遗漏。这次未读数缺失就是实例。后续应围绕服务端契约维护共享样本与各端解码测试，减少各端各自猜测字段含义。
- 某些兼容接口允许未识别字段被忽略，或对不支持的状态默认转换。后续按实际入口逐项收紧必填字段、枚举和响应校验，避免一次性修改所有接口破坏旧客户端兼容。
- Android `MainActivity.kt` 与三端 Go 适配器承担较多职责。更合适的整理方式是先按账号、会话、消息、媒体拆分；每次保留真实请求契约和现有回归。暂未进行大规模结构重写，也不能据此认定未检查接口都存在缺陷。
