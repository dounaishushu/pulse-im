# PC 启动时版本检查超时

## 原因

用户截图为“暂时无法加载聊天 / 无法检查客户端版本：signal timed out”。PC 2.4.169 的启动流程先 `await enforceClientUpdate()`，该函数访问公开的 `/client/update?platform=pc&version=...`，设置 10 秒超时；检查失败会抛出异常，外层 `boot()` 因此把整个页面替换为聊天加载失败页，尚未开始正常身份验证和会话加载。登录提交也会等待同一检查。

这个提示本身没有证明聊天记录损坏或登录过期。可确认的是客户端错误地将版本发现请求的失败作为聊天启动失败。截图没有请求当时的网络日志，无法进一步确定是 DNS、代理/线路中断还是接口响应变慢。本机对应用户数据目录没有可用于还原这次超时的诊断日志。

2026-11-17 02:41（北京时间）对当前配置的生产公开更新接口进行了两次不带凭据的 GET 检查：2.4.169、2.4.170 均返回 HTTP 200、`required=false`，各约 1.2 秒。该结果只反映检查时本机直接请求的状态，不能还原截图发生时的线路，也不能代替客户端代理场景或生产负载测试。原始时间与结果见交付目录的 `verification/public-endpoint-probe.json`。

## 修复

- 版本发现与身份验证并行运行，不再阻塞启动或登录提交。版本接口超时、网络异常、5xx 或无效响应不会替换现有聊天界面，不清理登录状态或草稿。
- 同一窗口合并并发检查；失败后按 15、30、60、120、240、300 秒退避，成功后每 5 分钟检查。网络恢复时可提前重试，重新可见时检查是否已到下一次检查时间。
- 明确的 `required=true` 或实时升级指令仍立即停止聊天工作并显示升级页。已确认升级要求不会被随后超时、普通更新响应或较晚返回的启动请求撤销。
- 主窗口和独立聊天窗口的启动响应均检查升级状态；Go 和旧协议的写请求都在进入发送路径前检查已确认的升级状态。下载链接继续限制为 HTTPS，文案继续转义。
- 真正的身份验证拒绝仍要求重新登录；真正的聊天 API 故障仍显示可重试的错误。记录版本检查失败到已有本地诊断通道，便于后续区分接口故障。

## 验证

`client-tests/pc-startup-version.test.cjs` 对实际发布文件中的函数运行 **16 项专项检查**，覆盖悬挂请求、截图中的超时原因、网络/503/403/无效响应、并发合并、重试退避、明确强制升级、升级后超时和普通响应、较晚身份/目录响应、真实身份拒绝和聊天 API 故障。全套客户端单元检查 **114 项通过**（包含原有更新契约检查），PC JavaScript 语法检查通过。

`client-tests/pc-startup-version-ui.e2e.cjs` 在隔离的本机服务与浏览器存储中加载发布 PC 页面，对主窗口及独立聊天窗口运行 **10 项页面检查**：

1. 保留真实版本检查的 10 秒 `AbortSignal` 超时，身份验证和聊天页面先完成；本轮受控响应中启动约 150 毫秒，不代表生产速度。
2. 版本响应未完成时，群消息和输入框已出现。
3. 等待真实超时后，原消息节点、输入框、草稿和保存的登录状态仍保留，没有整页失败提示。
4. 模拟网络恢复后后台重试成功，不重建会话，历史读取总数仍为 1 次。
5. 随后返回明确升级要求时显示升级页，Go 写请求在出站前被拒绝。

浏览器响应均由本机测试夹具提供，实时连接替换为进程内响应；未使用生产账号或向真实会话发消息。日志、截图、请求计数与源码指纹随安装包保存。

## 交付

PC **2.4.170 / Windows x64**，沿用现有生产 HTTPS/WSS 配置和安装方式。打包后核对 ASAR 内代码与当前源码、版本与生产配置，以及 EXE 文件版本资源和 SHA-256。现有 Windows 签名配置未改变。此次无需服务端部署，未推送 GitHub，也不修改 Android/iOS 版本。
