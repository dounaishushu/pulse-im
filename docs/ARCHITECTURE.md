# 单机后端架构设计

2026-11-10 更新。本文区分已实现机制与尚未验收的容量目标。完整业务范围为 30 模块、166 项，包含客户端需求。

## 已确认决策与组件边界

| 组件/工程 | 决策 | 作用与边界 |
| --- | --- | --- |
| Go | 单进程模块化单体 | HTTP、WebSocket、有限后台 worker；不做集群 |
| PostgreSQL | 持久事实来源 | 账号、登录会话、关系、消息、事件、待投递任务、业务数据 |
| Redis | 纳入基础架构，已接入 | 原子限流、30 秒一次性连接票据、75 秒 TTL 在线元数据；不保存唯一消息/唯一登录事实 |
| RocketMQ | 条件性评估，当前不启动 | 若需要独立部署的消费者、长时消息保留/回放或 outbox 无法满足经实测的任务积压，再做专项评估；不因“万人在线”自动增加 |

来源与许可记录保留在内部工程资料。产品名称、运行入口、公开 API、默认日志与部署产物统一为 Pulse IM。

## 当前结构

HTTP 与 WebSocket 共用身份服务；业务写入调用统一授权和 PostgreSQL 事务；同事务产生持久事件与 outbox。一个 dispatcher 按待处理状态领取任务并发送有界的变化通知。Redis 承载短期数据，正常消息事实永远从 PostgreSQL 补齐。

默认 go.work 只使用根模块，根模块名为 pulse.im/server。历史普通 CRUD 作为后续移植参考；任何被复用的流程仍要补齐权限及错误处理，不能重新挂回旧的全部路由。可复用代码与需替换的一致性内核区别对待。

## 资源预算与容量口径

目标是至少 10000 在线连接和日常聊天，不是每秒一万条消息。此前核实的旧服务器实际资源更高，验收必须把应用、PostgreSQL、Redis、代理和监控放入同一个 4 核总预算；GOMAXPROCS=4 不能代替整栈 CPU 限制。

8 GiB 起步预算：Go 约 1—1.5 GiB，PostgreSQL 约 2—3 GiB，Redis 上限约 384 MiB 数据/512 MiB 容器，代理/监控约 0.25 GiB，其余给系统、页缓存与余量。16 GiB 另测，不把空闲内存全部分给 Go 或数据库。

数据库池 max=16/min=2，连接超时 5 秒、SQL 超时 5 秒、锁等待 2 秒。shared_buffers 初始建议 1 GiB、work_mem 4 MiB、max_connections 40；这不是完整内存上限。SSD、fsync、WAL、同步提交保持开启。日志与附件有独立磁盘预算。

代码中的初始上限：12000 WS、256 个普通 HTTP 请求、128 个握手校验、每 socket 64 帧、所有发送队列计费上限 32 MiB、输入帧 4 KiB、请求体 32 KiB。变化通知通常数百字节，消息正文不上 WS 队列；队列预算不是应用 RSS 上限，仍包含连接、TLS、Go 堆和请求处理开销。

密码计算同时最多 2 个，每个 Argon2id 64 MiB；其余请求受控返回 503。登录按 IP/账号限流，每用户初始最多 8 个有效设备会话，这是资源保护初值，手机绑定策略另行实现。

## 身份与撤销

随机 256 位 bearer token 仅将 SHA-256 摘要写入 PostgreSQL，绑定服务端 session/user/device，30 天初始有效期。服务重启无需重新输入密码。重新登录同设备撤销旧会话；修改密码/冻结等事务须锁用户行并撤销相应会话。

每个 HTTP 请求验证持久会话；消息写入事务再次验证且短暂锁定用户/会话，防止只凭请求开始时的身份绕过已提交撤销。退出后立即关闭本进程对应连接。后台批量撤销的兜底扫描周期为 30 秒；消息读取/发送和通知接收者查询仍实时查有效状态，不依赖扫描才生效。

登录验证码、二步验证、手机绑定、完整管理端重置接口还未完成，当前账号由操作员 CLI 或隔离 fixture 创建。不能拿当前登录入口替换所有旧账号安全流程。

## 消息事务与顺序

1. 校验当前持久身份；普通发送与转发走同一 Send 入口。
2. 按 UUID 顺序锁目标会话，以及转发涉及的来源会话；检查成员、账号发言权限、频道角色、永久禁言、全员禁言、接收方临时聊天隐私和双方屏蔽。
3. 查 (conversation_id,sender_id,request_id) 唯一约束与请求摘要。相同请求返回同一消息；不同载荷返回 409。转发只接受 source_message_id，从库里读取当前可见正文。
4. 同事务递增该会话 message_seq/event_seq，写消息、事件引用、outbox；只有提交成功才返回成功。
5. 群发送不逐个更新成员摘要/未读数；公共会话只写一份序号，个人状态独立。

转发按来源 ID 计请求摘要，已提交重试返回原发送结果；首次操作总是检查当前来源可见性。已清空/个人删除的重试返回不带旧正文。文字编辑使用 expected_version 防止覆盖更新；内部撤回不复制正文到历史事件。

会话行仍是热点群串行点；当前读写吞吐需真实压测。发送、转发和文字编辑在锁会话前先获取按双方 ID 确定的私聊关系锁；拉黑、删好友和好友受理使用相同关系锁，再锁相关私聊。群禁言、成员退出和发送均先锁群会话，再检查成员权限。这样事务提交后的下一次发送按新权限判断。相关并发回归已通过，仍需在真实负载下评估热点关系与大群锁等待。

## 实时通知与断线恢复

outbox 使用有期限租约和 SKIP LOCKED 领取；不使用“最大自增 ID”作为提交水位。旧 worker 只能确认自己租约，失效租约可重新领取。成功投递尝试后删除 outbox，持久 events 保留用于补齐；删除 outbox 不代表用户已送达或已读。

每批最多 32 个 outbox 任务，同一会话/同一状态主体合并到较大版本，一次查询接收者，减少密集聊天的重复广播。只推送 conversation.changed / state.changed，不推正文。队列满或总内存超限则断开慢连接，以持久补齐恢复；不维护无限重试表。

接入顺序必须是：申请一次性票据 → 建 WS → 收到 ready → 获取全部会话分页和事件上界 → 固定 snapshot_max_seq 分页补齐，同时缓存变化通知 → 补到较新水位。ready 在连接注册完成并复查会话后发送，关闭握手与初始快照之间的漏通知窗口。每次重连重新获取票据并执行上述步骤。

同步扫描至多 100 个原始事件，过滤不可见消息也推进 next_after_seq，避免全被清空/删除时死循环。返回 message 当前版本，事件行不保存正文副本；撤回后读取早期事件也只返回空正文。客户端按消息 ID/version 合并，按事件页 next_after_seq 推进，不能拿 message.event_seq 替代页游标。snapshot 固定事件范围，不代表提供某个历史时刻的正文快照。

会话列表当前按 UUID 分页；客户端按需排序。群创建/邀请/退出/禁言等入口和个人清空/删除事件现已可用。成员新入群或重入群时按邀请的 allow_history 记录消息/事件起点；未授予时从此次加入后开始，授予时从 1 开始且仍过滤个人清空/删除。membership_version 每次重新加入递增，用于使旧缓存和旧同步失效。个人清空/删除及提醒使用独立的 personal_seq 和 personal_events，避免修改公共事件序号。过期事件重建协议待完成；当前不清理 events，尚无 retention 或 resync_required。

## 已读、送达、未读

read_seq/delivered_seq 单调增加，read 自动推进 delivered；不超过该会话已提交 message_seq。重复或倒序回执不写库。只修改该用户 user_states，不锁全会话写入行或给全部历史消息建回执。状态变化同事务进入 outbox，离线客户端通过 states 恢复自己的水位。群内阅读人不公开：其他成员仅收到匿名 receipts.changed，只有发送者可查询自己可见消息的聚合人数，频道不开放该统计。

单会话未读计数按可见范围查询，排除本人消息、撤回和个人删除；最多查询 cap+1 行，超过上限返回 truncated。会话目录中的批量未读摘要与长期历史的聚合优化仍待实现。标未读现在以个人 reminder 标志和持久个人事件同步，不回退 read_seq；旧前端显示尚待联调。

## Redis 故障语义

限流使用 Lua 将 INCR/首次过期原子完成；短期票据使用原子读取删除，长效 token 不进入 URL。Redis 断线时登录、票据与一般写接口返回 503，避免限流失效后无限放行；已有凭据的 GET 补齐和退出登录可在有限 HTTP 并发内继续使用 PostgreSQL。

在线状态用随机 connection ID 作为键的一部分并设 TTL，旧连接清理不会删除新连接。每 30 秒扫描已注册连接、按 256 条分批更新 Redis；Redis IO 不在全局连接锁内。在线状态仅为估计，后续对外读取还须隐私过滤。

Redis 使用独立实例/DB，建议 noeviction；容量耗尽要显式报错，避免限流票据被不确定淘汰。可重建缓存初版无 AOF 持久化，Redis 重启可能重置短期限流；若实际防刷要求需跨缓存重启保存，另行选择持久策略。Pub/Sub 不承担可靠消息。

## 性能代价与后续瓶颈

变化通知加受权拉取减少旧正文排队泄漏，但把一部分广播成本转化为客户端同步查询。客户端必须合并同会话提示，只运行一个补齐任务；不能每帧触发一次全列表或独立全历史请求。后续按测量再增加授权后共用投影/批量同步，不能为节省查询越过个人清空/屏蔽/撤回边界。

接收者 SQL 当前按目标群有效会话查询，一批对同会话只查一次；大群成员、持久 session 清理和在线索引仍需带历史数据评估。现阶段没有宣称可支持万人大群高频广播。Redis 也不能消除 PostgreSQL 提交和网络带宽成本。

## 后续业务与迁移

媒体需私有流式上传/下载、Range、即时授权与附件引用；目前未开放旧公开静态附件路由。定时分发/推送/任务工资用持久作业、有限 worker、幂等步骤和租约。工资按整数千分之一元，不接入停用钱包。

保留旧前端，后续逐端适配协议，不引入新客户端。原 MySQL 迁移需核实实际 schema、行数和线上补丁；在独立库演练账号/关系/消息/附件/作业，保留 ID 映射，仅迁移可验证单向哈希。无生产写库、切流或迁移已发生。

## 审查后的并发与回执约束（2026-11-10）

认证事务先锁用户行，再锁登录会话；同账号的会话撤销先取得用户排他锁，避免设备互撤死锁。关系写入沿用排序后的用户对锁；入群与屏蔽使用按用户分片的共享/排他事务锁，在会话锁之前取得。

清空使用客户端确认时的 through_seq，重试不得重新读取最新消息作为删除边界。清空不推进阅读或送达事实。个人清空/删除锁定本人的状态后，把未确认的消息区间记录至 receipt_exclusions；相邻或重叠范围合并，回执聚合使用最近的索引区间判断，避免后来读新消息替旧的隐藏消息产生回执。这仍需计入大群聚合容量测试；历史错误水位无法反推真实阅读。
