# PC 头像加载恢复

## 现象与原因

用户截图中，同一会话的列表头像显示破图，聊天顶部与消息头像能正常显示。针对发布的 `avatar-loader.js` 与 `message-view.js`，在受控响应中复现了两类问题：

- 列表稳定更新会删除模板中没有的 `data-avatar-load-state` 和 `data-avatar-load-placeholder`。这些属性属于头像恢复控制器；被删除后失败图片重新可见，出现浏览器破图图标。
- 失败条目按媒体身份共享。一次不可重试的旧授权/加载失败会一直被复用，新来源失败时也不重新恢复；而另一位置通过较新授权直接加载成功，原列表没有接收这次成功，仍保持失败。

这解释了为什么同一人的头像在两个位置会呈现不同状态。截图没有失败请求的状态码，不能单凭截图判定最初那次失败是授权过期、网络中断还是内容不可用；本次修复针对能够复现的客户端恢复缺陷。

## 改动

1. 稳定渲染器处理头像节点后，交回头像控制器核对加载状态，保持正确的默认占位，不再露出破图。正常消息附件不进入头像恢复策略。
2. 新头像来源允许重新恢复之前的失败；同一失败来源的确定拒绝仍保持限速，避免每次列表刷新都重新下载。
3. 头像已通过新来源解码成功时，修复当前页面里同一账号、同一媒体身份的失败或待加载副本；不重新下载已成功的头像，不替换其他人的头像。
4. 共享失败不能覆盖另一处已经解码成功的图片。修复后的节点和像素在列表刷新时保留，旧列表模板不能把它降回过期来源。
5. 已被成功来源替代的排队恢复任务不再执行。沿用账号代次检查、并发上限、字节上限与原生缓存的账号/来源校验，晚到响应不能更新切换后的账号。

## 验证

`client-tests/pc-avatar-recovery-ui.e2e.cjs` 直接加载发布的恢复与稳定渲染代码。修复前的 12 项基线中，4 项复现失败：刷新后占位丢失、顶部成功后列表不恢复、新来源不重新恢复及相应请求计数。基线日志与截图保存在交付目录的 `verification/before`。

修复后的 **17 项页面检查全部通过**，包含上述问题，以及临时 503 重试、重复拒绝不形成请求循环、保留已解码节点、不同媒体/账号隔离、账号切换后的响应失效。还加载完整 PC 页面，沿实际的 `GoV2 → 头像控制器 → 会话渲染` 路径验证：未读刷新保持占位，聊天顶部取得新 Go 媒体授权后列表一起修复，聊天历史只读取 1 次且草稿保留。页面检查使用本机夹具与模拟授权，不向生产聊天发消息。

原生 `pulse-avatar` 协议缓存增加旧授权失败、新授权成功、旧来源随后命中已验证缓存的检查；锁定账号后继续拒绝读取。全套客户端单元检查 **115 项通过**，PC JavaScript 语法检查通过。既有聊天首屏检查 **32 项通过**，覆盖 PC/Web 私聊与群聊的图片补齐、节点保留、阅读位置及重复打开。
